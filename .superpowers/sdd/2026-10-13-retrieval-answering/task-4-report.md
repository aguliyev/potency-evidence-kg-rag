# Task 4 report — answer records and CLI

## Implementation

`lib/potency_kg/answer_runs.py` provides `run_answer_batch(...)` and the reusable `answer_from_retrieval(...)` boundary. The batch embeds each of the six supplied questions once, passes that same query embedding to vector and graph retrieval, and resolves each question's cap from `max_evidence_chars_per_mode` or the shared `HybridRetrievalConfig.default_budget_chars`. P3 is capped at 6,000 Unicode code points; other questions use 16,000 by default. The batch writes P3 in both modes and the other five graph runs to the main JSONL pair (seven records), with the other five vector runs under `extra-mode/`.

Every attempted mode gets a UUID trace. A successful, locally citation-validated generation gets an answer row linked by `trace_id`; a provider, schema, retrieval, embedding, or citation-validation failure gets a `status="failed"` trace and no answer row. `failure_kind` is `provider`, `schema`, or `citation_validation`; `error_type` is recorded without the exception message. A deterministic empty-evidence gap is a successful answer. The trace carries the exact rendered `evidence_text`, separately records all pre-budget candidates and selected passage IDs, includes sent text per selected passage, provenance, truncation/dropped lists, config and config hash, prompt version and SHA-256, git commit, retrieval and snapshot versions, generation provider, model and sanitized origin, usage, attempts, timing, and citation check. The prompt resource is referenced by hash, not duplicated as a system prompt in the rows.

The `answer` CLI accepts `--config`, `--output`, and `--default-budget-chars`. It requires `KG_RUN_REAL_MODELS=true` with valid embedding and generation settings before constructing adapters. It reads the descriptor's `questions.json`, loads the scope's bound index version, uses `guard_output_path` on all four JSONL paths before writing, and checks protected-input hashes in the CLI's finally path. Output-path guards reject symlink aliases into protected inputs.

`results/evaluation/cases.jsonl` contains five candidate-authored cases beyond P1–P6: two development and three holdout, covering redaction, authority/status, indication scope, an unsupported universal-assay premise, and an absent numeric value. Every expected scoped `(source_id, source_version, passage_id)` reference was checked against `corpus/records.jsonl` with no missing references. `results/evaluation/holdout-freeze.json` records the pre-run UTC freeze timestamp `2026-10-14T00:59:29Z`, the whole-case-file SHA-256 `0913887ad1acc30f0ac27778fae41715329a8f4dc2ad2542b4a051c8054df700`, and holdout-row SHA-256 `cfc57331b8a0f302027a91f943743a528a995ef0d6cdadbe22a75f669a988028`. The holdout digest is over `jq -c 'select(.split == "holdout")'` UTF-8 output including final newlines. These cases are evaluation inputs only; the answer CLI reads only `questions.json` for questions and only bound source passages for evidence.

## Task 5 interface impacts

Fixture answer callbacks should call `answer_from_retrieval(question_id, question, "graph", retrieved, scope, corpus_snapshot, generation_client, max_evidence_chars, config, git_commit=...)`. It consumes the already completed stage `RetrievalResult`; it makes **no** embedding, retrieval, database, or output-write call. It returns `(answer_row_or_none, trace_row)`. The caller appends `scenario_id`, `stage`, and `run_id` to the returned row(s), writes a trace even when the answer is `None`, and places both in the appropriate fixture history and aggregate JSONL paths. It must use the same `config` that produced `retrieved` (a mismatch is a failed schema trace). The trace includes `selected_passages[].sent_text`, `selected_passage_ids`, `candidate_passage_ids`, `evidence_text`, `graph_version`, `index_version`, usage, attempts, and failure metadata. Task 5 remains responsible for its own guarded fixture/history paths and the before/after source snapshots; the main batch writer is specific to assignment questions and main/extra-mode routing.
